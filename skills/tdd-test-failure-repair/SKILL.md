# tdd-test-failure-repair

Use this skill after `run_tests` reports a failing current batch.

## Instructions

1. Treat the latest `run_tests` output as the source of truth.
2. Classify the failure before editing: implementation logic, boundary wiring, selector/render state, persistence/test database, framework/config, generated test defect, or test content.
3. Re-read the failing test file and the nearest owner implementation file before making another edit.
4. Compare the failure against the current UI/API/FUNC/DB interface chain; if a downstream layer is missing or disconnected, repair the chain rather than patching only the surface assertion.
5. If the same fingerprint repeats, replace the current hypothesis or move one layer outward instead of patching neighboring files from momentum. If ARC_TEST_FILE_STATUS reports STALL DETECTED (same fingerprint 3 times in a row), rotation is mandatory: re-classify the failure, list the hypotheses already tried, and edit a different layer of the UI/API/FUNC/DB chain or a different fix approach within the same layer.
6. If product behavior is wrong, edit product code. If a generated test is invalid, contradictory, brittle, or incompatible with the runner, edit the current node's test while preserving requirement intent. For runner setup failures, repair editable package scripts or a current node helper (in the declared write set when stage pipeline is active). In pipeline mode shared runner configuration and fixtures are read-only: when the fault can only be fixed there, stop retrying file edits and hand off the failure fingerprint, affected path, and concrete coordinator/template repair action. Never report `IMPLEMENTED` for this failing run.
7. Make one minimal contract-preserving fix, then call `run_tests` again. Work file-by-file when the layer has several red files: verify each red file green with `run_tests(test_files=[...])`, then close the layer with one passing full-layer run.
8. Continue after failing runs while the active layer's tool budget remains and an editable repair exists. A fault confined to read-only shared infrastructure requires the failure handoff in step 6, not repeated forbidden edits or a success claim.
9. Say `IMPLEMENTED` only when the system indicates the active layer passed and no scheduled layer remains blocked by the current session.
10. Each current-node test layer has an independent `run_tests` budget of 10 calls. After a failure, spend enough effort to localize and repair the cause before consuming the next call.
10a. When run_tests reports a missing npm package (for example `Cannot find module 'cookie-parser'` or `missing dependency: cookie-parser`), repair it with one `install_dependencies(package='...', target='backend'|'frontend')` call and re-run run_tests. Prefer an installed well-known package over hand-rolling crypto/cookie/parsing code; prefer Node built-ins (`node:crypto` scrypt, `node:cookie`-style manual parsing only when trivial) only when the install fails. The install does not touch package.json or the lockfile.
10b. Read-only forbidden zones: `node_modules`, `dist`, `dist-ssr`, `build`, `coverage`, `.vite`, the lockfiles (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`), and `.arc` (except `.arc/tdd_runs`). Do not glob, grep, or read them, not even to confirm an install or a build worked. An empty or permission-denied glob/grep/read there does not mean the file does not exist — matches under denied subtrees are withheld, not listed. The only valid verification of an environment repair is `run_tests`. If the layer is already closed (`ARC_TDD_HARD_STOP`), run_tests is closed too: record the repair action in the failure report and finish the pass instead of probing the forbidden zones.
11. For auth/session failures, use the auth-session-consistency skill and repair the shared session path first: session persistence, current-session API, client session loader, global provider/state, shell/header consumers, and route behavior.
12. If Playwright reports an unknown fixture parameter, inspect the `test.extend` block and make the fixture name and `use(...)` value match before rerunning.
13. If Playwright or Testing Library reports multiple matches for a label, do not retry with a broader selector. Use an exact accessible role, a stable id, or a scoped locator that identifies one element.
14. If the same backend database singleton error repeats, inspect the database runtime helper and initialization lifecycle before changing unrelated tests or UI files.
15. When repairing a contradictory generated test, re-check the requirement scenario: GIVEN remains setup, WHEN remains action, THEN remains assertion. Preserve the scenario intent instead of weakening it to match current implementation.
16. For cart, checkout, account, product, order, catalog, inventory, or persisted user-owned data failures, repair the connected domain path first: data source, API route/client, service logic, persistence/runtime state, shared consumer, and visible UI.
17. If the failure is a missing pre-existing record, relationship, permission, status, or list item described by the requirement, inspect and repair the schema/repository/seed/bootstrap/startup path first. Do not patch the UI with hardcoded rows or add test-only database setup.
18. Begin each repair with the failing manifest test, its direct owner file, the current-node interface contract, and the exact failure output. Read configuration, shared runtime, or neighboring layers only when that evidence points there; do not restart project-wide exploration.
19. If the E2E failure body contains `=== Backend Process Output ===`, read that section first: it is the backend server's own console output, and a stack trace there (for example Express 5's bare-wildcard throw `TypeError: Cannot read properties of undefined (reading 'type')` from `app.get('*')` or `app.use('*')`) means the server crashed at startup. Fix the crashing registration (use a regex or `'/{*splat}'` for SPA fallback) instead of editing tests or runtime wiring.

20. When a full-layer run passes, the layer is done: do not keep editing its tests or covered code. Re-editing a green layer risks turning it red again and spending the budget recovering a state you already had. Move to the next layer or return `IMPLEMENTED` per the layer ladder.
21. Never silence a failing test by adversarial means: no zero-width/invisible characters inside label text, no deleting assertions, no widening matchers beyond what the requirement states, no renaming visible UI text so a strict locator stops matching. If `getByText`/`getByLabel` reports multiple matches, fix the semantic structure - distinct accessible names, `role="alert"` for error messages - rather than obfuscating one of the matching elements.
21a. When a failing UI test targets a requirement-quoted accessible name or message that the implementation renders differently (a translation, a concatenation, or a rewording), the requirement text wins: change the implementation so the control's accessible name is exactly ONE requirement-quoted literal (prefer the primary, first-quoted one) - anchored or exact matchers such as `getByLabel(/^密码$|^password$/i)` fail on concatenated text like `密码 Password`, so never merge several quoted literals into one visible string. When several requirements reference the same shared control, ship a literal that every referencing requirement explicitly quotes (the intersection of their quoted-literal sets); only when no single quoted literal satisfies every referencing requirement is concatenation the sanctioned exception. Never repair by rewriting the test's selector to wording the requirement does not state.
21b. When a test fails to find an error message that the backend actually returned, repair the error presentation path, not the assertion: render validation/API errors as visible text in the requirement's language inside a `role="alert"` (or `aria-live`) region, associate field errors with their inputs (`aria-invalid` plus `aria-describedby`), and never surface errors as color-only styling.
22. When a React test asserts an exact count of effect-driven calls (fetch, subscriptions), check the render environment for StrictMode first: it double-invokes effects by design. Either the component deduplicates intentionally (guard inside the effect) or the assertion accounts for it; do not burn run_tests calls re-asserting the same count after neighboring edits.
23. If Playwright E2E fails with blank pages, 404ing assets, or element-not-found for controls whose source exists, classify it as lost template runtime wiring before touching selectors: verify `frontend/dist/index.html` exists, that the backend entry still serves it through the template's `express.static` + SPA fallback with dist resolved relative to the backend module directory (worktree CWD), and that no hand-rolled `sendFile` chain or temp-copy dist snapshot replaced it. Restore the template's serving semantics with additive edits - the file tools reject whole-file rewrites of these surfaces (app entry, server/DB bootstrap, root render) on purpose, and reimplementing them is how a 2-second fix becomes a 45-minute blank-page loop.
24. Batch-timeout signature: when `run_tests` returns `Command timed out after N seconds.` with no per-test results (no `ok`/`failed` lines, no `ARC_TEST_FILE_STATUS`), the E2E runner killed the whole batch at its runner cap - that is not a test verdict, and re-running the unchanged full layer reproduces it deterministically, so it is the lowest-value budget spend available. The output is missing because the runner discards partial output on timeout, not because nothing ran. Before spending the next call: (a) read the failure artifacts that survived the kill under `backend/test-results/<failed-test>/` - `error-context.md` names the test and shows the page snapshot at failure, `trace.zip` records the exact action it was stuck on; (b) do the arithmetic: each failing scenario burns its full per-test timeout (30s in the template's `playwright.config.js`), so a handful of red scenarios exceed the runner cap - fix the identified failures before spending another full-layer call; (c) if the artifacts show the batch died before any test failed, add a fast diagnostic probe (one `page.goto('/')` plus a visible-shell assertion) so the next run separates environment faults from test failures in seconds.
25. When an E2E batch keeps dying at the runner cap with several failing scenarios, shrink the blast radius so a failure fits inside the cap and becomes visible: `test.describe.configure({ mode: 'serial' })` stops the batch at the first failure and skips the rest, converting a blind kill into one visible failure with its error context and trace. Serial mode is also the legitimate final shape for stateful scenario chains that build on prior tests' state; either way the layer still closes on a green full run.
26. If Playwright E2E fails with `fill`/`click` timing out while the page snapshot shows the form frozen in its initial state, suspect an accessible-name mismatch before touching app logic: generated specs locate controls with `getByLabel(..., { exact: true })` or anchored role matchers against the requirement-quoted names, so a trailing colon (`用户名：` vs `用户名`) or any decoration appended to a label breaks every form interaction while substring-matching component tests stay green. Repair direction follows 21a: align the implementation's rendered accessible names to the requirement-quoted literals (delete the decorative suffix); never widen the spec's `exact: true`/anchored matcher to absorb the decoration.
27. An unknown-symbol error (`X is not a function`, `X is not defined`, `has no exported member`, `Cannot find module`) proves only that the symbol as written does not resolve in this environment - it does not say whose fault it is, and the owners have different fixes. Classify before editing: (a) a misspelled or nonexistent API name - resolve the real name from working in-repo callers, template helpers, or the dependency's declared interface (package.json/lockfile; never grep or read node_modules), then fix the call site - and note the installed version may genuinely lack the API, in which case use what the installed version offers; (b) `Cannot find module` naming a third-party package - that is a missing dependency: make one `install_dependencies` call and re-run run_tests, do not rename imports or hand-roll a replacement; (c) the object not being the type you assumed (`res.send is not a function` where `res` is an error object) - fix the object's source, not the method name; (d) a missing test-environment global or polyfill (`matchMedia`, `fetch`) - fix the test setup, not product code.
28. A repeated identical query is never new evidence. After the same search (same tool, same pattern, same scope) has run twice with no successful edit in between, stop re-running it: either act on the evidence already returned (make the edit it points at) or switch evidence channel (read the file directly, call run_tests). The runtime answers further identical searches with a replay of your own earlier result plus this notice - further repeats return the same replay, not a fresh search, so a loop can only end in an edit or a different channel.
