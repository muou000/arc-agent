## ARC 编译速度分析（harness 设计视角）

对 arc-agent 代码做了性能根因审查，定位影响编译速度的 harness 级缺陷（非"节点多"本身）：

1. **无 checkpointer**：全仓无 `checkpointer/MemorySaver`；`agents/runtime/runners.py:753` `build_agent_config` 只传 `thread_id`+`recursion_limit`，thread_id 无持久化即空转。TDD 重试每次都是全新会话，需重读 SKILL.md、重读文件、重推方案。
2. **每阶段重建 agent**：`build_stage_agent` 在 `run()` 内部调用（`agents/interface_designer.py:73`、`test_generator.py:86`、`test_driven_developer.py:185`），每次新建模型客户端（`agents/runtime/factory.py:113`、`agents/model/openai_api_adapter.py:154`），连接池不复用。
3. **上下文缓存每轮清空**：`agents/context/pipeline.py:85` `configure()` 内 `cache.clear()`，而每个 `run()` 开头都调 `configure()` → `get_or_compute` 形同虚设。`pipeline.py:400` `_get_existing_interface_cards` 遍历整张 interfaces 表，整体 O(N²)。
4. **队列严格串行**：`core/workflow.py:283-289` `_drain_runnable_tasks` 单 task 循环，无并发调度（兄弟叶子本可并行）。
5. **E2E 无产物缓存**：`app_type_handler/web.py:982` e2e 分支无条件 `_build_frontend_dist`（`npm run build` 超时 120s）→ db prepare → 后端启动轮询 20s → playwright 120s → 端口清理。单次 E2E 可达 2–4 分钟。
6. **TDD 循环放大**：`core/phases.py:17` 每层预算 10；`phases.py:429` `max_sessions = 10 × 层数` ≤30 会话/节点。`phases.py:489` 层失败仍前进（Unit 挂也跑 E2E）。`core/workflow.py:276` 全队列跑完后再对失败节点自动重试一轮。
7. 其他：强制每会话 `read_file` 所有 SKILL.md（`prompts/common.py:127`；**实测校正**：`skills/` 目录总量 609K 但那是含 assets 的目录大小，真正进上下文的只有 10 个 `SKILL.md`，合计约 48K，最大 9.4K，每阶段选 2–4 个 → 约 15–30K / 5–9K tokens；112K 的 `vercel-react-best-practices/AGENTS.md` 按策略不可读，不进上下文）；日志在关键路径同步写盘（`core/logging.py:31` 每事件 `open('a')`）；模型重试退避 2s→30s（`openai_api_adapter.py:26`）；`disable_streaming=True`；`recursion_limit=5000`；每次初始化跑两次 `npm install`（`app_type_handler/base.py:64`）。

结论：成本按 `节点数 × 阶段数 × 重试次数 × 全量上下文重发` 叠加，优化优先级应为 会话持久化 > agent/模型复用 > 上下文缓存 > 并行调度 > E2E 产物缓存。

## 环境注意：该 worktree 里 git 提交有沙箱陷阱

本仓库是 `D:/code/arc-agent` 的 linked worktree。沙箱会**回滚 `git commit` 对分支引用的写入**（`.git/refs/heads/workbuddy/` 整个目录会被抹掉），但 commit 对象本身已经正确落盘。症状是提交后 `git log` 报 `does not have any commits yet`，若此时再提交就会产生 218 文件的 root commit 污染历史。

可靠流程（每项提交都按这个走）：
1. `git add <明确文件>` → 确认 `git diff --cached --name-only` 只有预期文件；
2. `git commit -F <消息文件>`，从输出里读短哈希；
3. `git rev-parse <短哈希>` 拿完整哈希，并核对 `git log --format='%P' -1 <哈希>` 的父提交是否正确；
4. **用文件写入工具（不是 shell）** 创建 `D:/code/arc-agent/.git/refs/heads/workbuddy/main-9c8d06d6`，内容为「完整哈希 + 换行」——写入工具能建目录，shell 建不了；
5. `git log --oneline` 复核线性历史。

另外：`.git/index` 的写入是能跨命令保留的，只有 refs 会被回滚；`git reset --mixed` 在 HEAD 未 born 时会失败，所以修复历史前必须先修好分支引用。
